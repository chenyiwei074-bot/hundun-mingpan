## 1. `/api/receipts`：两个端点、一个契约，前端已经在调用

前端调用点：`frontend/lib/receipt/anchor.ts`（提交 + 查状态两处），它已经在生产页面上真的发出去了。

**POST `/api/receipts?visitorId=<游客 id>`**
- 请求体：`receiptSubmissionBody(receipt)`，只带摘要与结构字段，不带原文（原始问题/姓名/生辰/户型图不进这一发）。
- 期望响应：`{ ok: true, day: 'YYYY-MM-DD', already: boolean, leaf: '0x…' }`；失败时 `{ ok: false, error: '…' }` 且 HTTP 非 200 也算失败。
- 前端行为：`ok=false` 或 HTTP 非 200 → 回执卡上写失败原因，不假装提交成功。

**GET `/api/receipts/<recordHash>`**（recordHash 是 64 位 hex，不带 `0x`）
- 期望响应按 `state` 分三档，前端**只认 `unanchored` 与 `pending`**，其它一律显示「状态未知」：
  - `{ ok: true, state: 'pending', day, leaf, root?, prevRoot? }` → 文案「已进 <day> 的 Merkle 台账」
  - `{ ok: true, state: 'unanchored', day, reason? }` → 文案「<day> 尚未封账」
  - HTTP **404** + `{ ok: false, error }` → 前端当作"这份摘要尚未提交"（404 是唯一有语义的非 200）
- 其它状态码/形状不合 → 前端显示查询失败，不回落成"未提交"。
- 需要运维定的两件事：① `anchored`（已上链/已升级）这一态到底怎么拼写、要不要给 `proof` 字段；② 同一 hash 重复 GET 是否有频控（前端没有重试环，5xx 不自动重发）。

**怎么算验过了**：拿一张真实回执的 `recordHash`，先 GET 得到 404（未提交），POST 一次，再 GET 应回 `pending` 且 `day` 是已封账或待封账的那一天。两步都截屏留档即可。
